# 工作原理

本文记录工具依赖的协议细节与实测踩坑结论，供改编到其他学校环境时参考。

## 一、认证体系

目标网络使用 Dr.COM（城市热点）网关，认证页由网关的 80 端口提供，接口在 801 端口。特征：

- 门户首页 `GET /`：未认证时返回登录页；已认证时返回注销页，页面内嵌 `uid='账号@运营商'`、`v4ip='本机IP'`。
- 登录页脚本为 `a79.htm` 及其配套的 `aNN.js`，登录通过表单 POST 提交。
- 801 端口提供 JSONP 形式的会话查询、注销、MAC 解绑接口。

新版 `/eportal/portal/login` JSONP 登录接口在本环境返回「没有配置接入服务器」，因此只能走 `a79.htm` 表单通道。

## 二、关键接口

| 用途 | 请求 |
| --- | --- |
| 登录 | `POST {portal}/a79.htm` |
| 在线查询 | `GET {portal}:801/eportal/portal/online_list?callback=cb&user_account={账号}&jsVersion=4.1.3` |
| 注销 | `GET {portal}:801/eportal/portal/logout?...&wlan_user_ip={IP}&wlan_user_mac={MAC}&jsVersion=4.1.3` |
| MAC 解绑 | `GET {portal}:801/eportal/portal/mac/unbind?...&wlan_user_mac={MAC}&wlan_user_ip={IP}` |
| 掉线探测 | `GET http://connect.rom.miui.com/generate_204`（期望 204） |

### 登录提交字段

```
DDDDD=<账号>&upass=<密码>&R1=0&R2=&R3=0&R6=<1 手机 / 0 电脑>&para=00&0MKKey=123456&v6ip=
```

判定成功的标志是返回页内含「认证成功页」或 `Dr.COMWebLoginID_3`。若返回 `clientip online`，说明该 IP/MAC 已有会话，需要先注销。

### 终端类型与名额

`phone_flag` 是服务端对会话的终端标注，**由 `R6` 字段决定，不是 User-Agent 决定的**（UA 只影响页面跳转，可一并伪装以保持一致性）：

- `R6=1` → `phone_flag=1`，计为手机名额；
- `R6=0` → `phone_flag=0`，计为电脑名额。

实测同一账号可同时持有 1 个电脑名额 + 1 个手机名额（两台设备各占其一，互不干扰）。

### MAC 绑定（容易踩的坑）

AC 会以「MAC + 终端类型」为键记录终端身份。仅切换 `R6` 重新登录不会改变 `phone_flag`，必须先调用 `mac/unbind` 清掉本机 MAC 的旧记录，再登录，新类型才会生效。反之，一旦某 MAC 被登记为手机终端，之后注销重登仍会沿用手机身份。

## 三、请求实现要点

工具用 `System.Net.HttpWebRequest` 直接发请求，有三处必须处理：

1. **关闭 `Expect: 100-continue`**：`.NET` 默认添加该头，Dr.COM 网关对此不应答，导致 POST 挂起或认证失败。需设置 `ServicePoint.Expect100Continue = $false`。
2. **绕过系统代理**：机器上若存在 `http_proxy` 或 WinHTTP 代理，访问内网门户会被转发到代理而失败（表现为 502 或连接超时）。需设置 `$req.Proxy = $null`。
3. **不复用失效连接**：Wi-Fi 重连后进程内的 Keep-Alive 连接已失效，报「无法连接到远程服务器」。请求失败后应丢弃连接（`KeepAlive = $false`），并在异常处理里取 `InnerException` 的最内层，才能看到真实原因（如 `SocketException`）。

## 四、状态判定与重连策略

单次重连的顺序：

1. 探测门户是否可达（80 端口首页）。不可达则不打日志刷屏，直接等待下一轮。
2. 查询在线会话，**按本机 IP、其次按本机 MAC 匹配出属于本机的会话**；已在线且名额正好符合所选终端类型 → 什么都不做，避免打断正在使用的连接。
3. 名额不符 → 注销 → 解绑 MAC → 登录。
4. 登录失败 → 注销后重试，最多 2 次。
5. 连续失败按 30/60/120/240/300 秒退避，成功后复位。

会话查询失败不等同于掉线：801 接口偶发返回空列表，此时改用 80 端口门户首页判断（已认证会返回注销页），只有两者都不通过才判定掉线。

## 五、常见误判与修正

| 现象 | 根因 | 修正 |
| --- | --- | --- |
| 明明在线却反复重登 | PowerShell 把单元素数组展开，`.Count` 为 `$null` | 用 `return @($list)` / `,$arr` 强制返回数组 |
| 名额判断错误、日志写着“电脑名额”但其实已切到手机 | `online_list` 返回的是该账号**所有设备**的会话，取 `[0]` 会拿到别的设备 | 按本机 IP → MAC 精确匹配，匹配不到视为本机未认证 |
| 在线但名额不符时工具毫无反应 | 定时器只在判定“离线”时才重登 | 在线且名额不符也要触发一次“注销 + 解绑 + 登录” |
| 两个实例互相注销 | 多开导致会话被反复踢掉 | 全局互斥量 `Global\DrcomCampusNetHelper` 做单实例保护 |
| 登录成功后立刻查到旧状态 | 服务端同步延迟约 10 秒 | 登录后延时并多次重试查询 |

## 六、安全与合规边界

工具只做“把手工填表这一步自动化”：全部请求都由本机发起，使用本人账号密码，不抓取他人凭据、不修改计费数据、不绕过任何鉴权。终端类型选择属于用户对自身账号的使用方式，是否被学校允许以用户协议为准。
